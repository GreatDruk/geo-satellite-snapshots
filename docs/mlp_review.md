## Почему GPU мог быть быстрее всего вдвое

Это сообщение пользователя; локального GPU-лога нет, поэтому причина не измерена. Сначала проверьте metadata.json Kaggle-запуска: device должен быть cuda, а не cpu. В будущих metadata также сохраняются gpu_name и число CPU-потоков PyTorch.

В текущем pipeline есть несколько вероятных ограничений:

1. JPEG читается и декодируется, resize/аугментации выполняются на CPU. GPU не ускоряет эти операции автоматически. Разные CPU и файловые системы локально/Kaggle не позволяют приписать всё отношение времён одному GPU.
2. У компактной MLP короткие вычисления на batch; доля загрузки и запуска операций может быть большой. Batch=128 у 64/96 MLP не выглядит заведомо маленьким. У 256 MLP batch=64, но там намного больше вычислений; без GPU utilization и профиля нельзя выбирать новый batch вслепую.
3. Ранее workers заново запускались при каждой итерации train/val. На маленькой модели этот накладной расход может быть заметным.
4. Передача тензоров выполнялась блокирующим вызовом .to(). Pin memory сама по себе не гарантирует перекрытия передачи и вычислений.
5. .item() для loss/accuracy синхронизирует host с GPU; сохраняются также checkpoints, которые не ускоряются пропорционально вычислительной мощности GPU.

GPU ускоряет вычислительную часть, но wall-clock зависит от всего pipeline. Величина ×2 сама по себе не доказывает ошибку использования устройства. Эти гипотезы соответствуют [рекомендациям PyTorch по производительности](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html) и [передаче pinned memory](https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html); конкретное узкое место здесь не профилировалось.

## Изменения для будущих CNN/ResNet

- Только в CNN/pretrained-конфигах включены persistent_workers=true, prefetch_factor=2. num_workers оставлен 2. У старого baseline_cnn также включены workers=2 и pin_memory=true, чтобы базовый запуск на GPU не оставался с синхронной загрузкой по умолчанию.
- При num_workers=0 эти параметры отключаются/игнорируются корректно; на Windows CPU остаются workers=0 и pin_memory=false.
- На CUDA с pinned DataLoader используется non_blocking=True в train/val/predict. Это разрешает неблокирующую передачу, но не обещает полного перекрытия без дополнительного CUDA-stream prefetcher.
- Повторное чтение loss.item() в одном batch убрано. Проверка конечности loss и синхронизация для неё сохранены; полностью асинхронным цикл не стал.
- В новых history.csv появятся train_time_sec и val_time_sec отдельно. Оба включают загрузку соответствующего split; это не отдельный замер чистого CUDA compute/data wait.
- MLP-конфиги и сохранённые результаты не менялись. Общий pipeline получил изменения передачи/замеров, которые не переписывают результаты прошлого обучения. Для MLP persistent workers не включены.

Сохранение workers меняет поток случайных аугментаций и генератора между эпохами по сравнению с их перезапуском. Новые будущие запуски будут воспроизводимы в рамках одинаковой политики workers/seed, но не обязаны совпадать с прежним pipeline с перезапуском workers.

## Проверка конфигов

Все пять CNN-конфигов прошли сборку, forward/backward на синтетических изображениях выбранного размера и создание optimizer/scheduler. Проверены выход на 20 классов и конечные gradients. Во всех device=auto и deterministic_warn_only=true. Cosine-конфиги имеют T_max=epochs; baseline_cnn сохраняет исходный Adam и постоянный LR как простой ориентир.

Для всех четырёх ResNet-конфигов проверены разрешённая архитектура, имена ImageNet-весов, mean/std, более низкий LR тела, выбранные блоки, warmup<epochs и cosine-график. Тесты на маленьком backbone подтверждают заморозку весов/BatchNorm, смену режима и группы optimizer. Реальное создание torchvision ResNet и CUDA backward локально не проверены: torchvision/CUDA недоступны. Качество и GPU-скорость CNN/ResNet пока не измерены.

Размер batch оставлен 32 для CNN 256 и ResNet, 64 для компактных CNN. Без измерения памяти/скорости конкретного Kaggle GPU увеличивать его преждевременно. Начать можно с cnn_256_balanced и resnet18_head_only, затем сравнить resnet18_partial/full и resnet50_partial.
